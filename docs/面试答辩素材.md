### 🔥 坑 1：Linux VM 无法访问外部互联网

**场景描述**  
项目初期部署时，Linux 虚拟机（192.168.1.100）无法访问外部网络，导致 DashScope API 调用完全失败，整个对话系统无法工作。

**问题现象**
```
$ ping -c 3 47.98.198.153
connect: No route to host

$ curl https://dashscope.aliyuncs.com
curl: (6) Could not resolve host
```

**根因分析**
1. 默认网关 `192.168.1.2` 不可达（ARP 解析失败）
2. DNS 服务器无法解析外部域名
3. VMware 虚拟网卡配置问题

**解决方案**
1. **在 Windows 主机上启动 HTTP 代理服务器**，转发所有外部请求
2. **配置 Dify 使用代理**访问外网服务
3. **修改 Linux 网关**指向 Windows 主机

**关键代码/配置**
```python
# Windows 主机上运行代理服务器
# proxy_server.py
from http.server import HTTPServer, BaseHTTPRequestHandler
import urllib.request

class ProxyHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self._proxy()
    
    def do_POST(self):
        self._proxy()
    
    def _proxy(self):
        # 实现 HTTP 代理转发
        # 支持 CONNECT 方法用于 HTTPS 代理
        pass

server = HTTPServer(('0.0.0.0', 8888), ProxyHandler)
server.serve_forever()
```

```bash
# Linux VM 上配置网关
ip route add default via 192.168.1.1 dev ens33

# 配置 DNS
echo "nameserver 8.8.8.8" >> /etc/resolv.conf
```

**验证结果**
```bash
$ curl https://dashscope.aliyuncs.com
# 返回 200 OK，成功访问外部 API
```

# password = "MTIzNDU2"

# Step 2: 发送登录请求
response = requests.post(
    'http://localhost/console/api/login',
    json={
        'email': 'difyadmin@dify.com',
        'password': password  # Base64 编码后的密码
    }
)
# 返回: 200 OK, 登录成功
```

### 🔥 坑 3：模型凭据加密/解密失败

**场景描述**  
在 Dify 控制台配置阿里云 DashScope API Key 后，系统无法正确解密凭据，导致 `KeyError: 'dashscope_api_key'` 错误。

**问题现象**
```
POST /v1/chat-messages
响应: {"code":"invalid_param","message":"Run failed: req_id: xxx PluginInvokeError: ... KeyError: 'dashscope_api_key'"}
```

**根因分析**
1. Dify 使用 RSA 加密存储模型凭据
2. 数据库中存储的加密凭据与当前 RSA 密钥不匹配
3. 插件守护进程从凭据中获取 API Key 时失败

**解决方案**

**方案 A：重新生成 RSA 密钥对**
```python
# 在 API 容器内执行
docker exec -it docker-api-1 python

from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa
from cryptography.hazmat.backends import default_backend

# 生成新的 RSA 密钥对
private_key = rsa.generate_private_key(
    public_exponent=65537,
    key_size=2048,
    backend=default_backend()
)

# 保存密钥
private_pem = private_key.private_bytes(
    encoding=serialization.Encoding.PEM,
    format=serialization.PrivateFormat.TraditionalOpenSSL,
    encryption_algorithm=serialization.NoEncryption()
)

# 更新 SECRET_KEY 环境变量
# 重启服务
```

**方案 B：修改插件代码绕过问题**
```python
# 修改 llm.py 中的凭据获取方式
# 将硬编码的字典访问改为安全获取

# 错误写法 (会导致 KeyError)
api_key = credentials["dashscope_api_key"]

# 正确写法 (安全获取)
api_key = credentials.get("dashscope_api_key", "")
if not api_key:
    raise ValueError("dashscope_api_key not found in credentials")
```

### 🔥 坑 4：Nginx 反向代理路由配置错误

**场景描述**  
配置公网访问后，部分 API 返回 404 错误，插件请求无法正确转发。

**问题现象**
```
GET http://YOUR_PUBLIC_HOST:8082/console/api/apps
响应: 404 Not Found

GET http://YOUR_PUBLIC_HOST:8082/plugin/management/models
响应: 404 Not Found
```

**根因分析**
1. Nginx 配置文件缺少 API 路由规则
2. `/plugin/` 路径未正确转发到插件守护进程
3. 路由规则的优先级和匹配逻辑设置不当

**解决方案**
```nginx
# /opt/dify/docker/nginx/conf.d/default.conf

server {
    listen 80;
    server_name _;
    
    # ===== 关键：路由规则的顺序很重要 =====
    # Nginx 采用最长前缀匹配原则
    
    # 规则 1: 控制台 API (最精确的路径)
    location /console/api/ {
        proxy_pass http://api:5001/console/api/;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 300s;
        proxy_buffering off;
    }
    
    # 规则 2: 插件请求
    location /plugin/ {
        proxy_pass http://plugin_daemon:5002;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 300s;
    }
    
    # 规则 3: 公共 API
    location /api/ {
        proxy_pass http://api:5001/api/;
        proxy_set_header Host $http_host;
        proxy_read_timeout 300s;
    }
    
    # 规则 4: 用户 API (v1)
    location /v1/ {
        proxy_pass http://api:5001/v1/;
        proxy_set_header Host $http_host;
        proxy_read_timeout 300s;
        proxy_buffering off;  # 重要! SSE 流式响应需要
    }
    
    # 规则 5: 前端页面
    location /console {
        rewrite ^/console(.*)$ /$1 break;
        proxy_pass http://web:3000;
    }
    
    location /app {
        proxy_pass http://web:3000/app;
    }
    
    # 默认路由
    location / {
        proxy_pass http://web:3000;
    }
}
```

**关键知识点**
- Nginx 路由匹配采用 **最长前缀匹配** 原则
- `/console/api/` 会匹配 `/console/api/...` 但不会匹配 `/api/...`
- SSE 流式响应必须设置 `proxy_buffering off`
- LLM 请求超时时间要设置足够长（300s 以上）

### 🔥 坑 5：工作流同步卡住

**场景描述**  
进入 Dify 工作流编辑器时，页面一直显示"同步数据中"，无法加载。

**问题现象**
- 前端页面长时间显示加载动画
- 插件列表无法加载
- 工作流节点拖拽不响应

**根因分析**
1. 插件守护进程数据库 `dify_plugin` 中缺少必要的插件记录
2. `workflow_tools_manage_service.py` 报告 `workflow not found` 错误
3. 前端轮询同步状态时无法完成

**解决方案**
```sql
-- Step 1: 查找引用不存在工作流的工具提供者
SELECT * FROM tool_api_providers 
WHERE workflow_id NOT IN (SELECT id FROM workflows);

-- Step 2: 删除无效的引用记录
DELETE FROM tool_api_providers 
WHERE workflow_id NOT IN (SELECT id FROM workflows);

-- Step 3: 检查插件记录是否完整
SELECT * FROM plugin_chains;
SELECT * FROM plugin_model_providers;

-- Step 4: 重启相关服务
docker compose restart api
docker compose restart plugin_daemon
```

**调试技巧**
```python
# 查看 API 日志中的错误
docker compose logs --tail 100 api 2>&1 | grep -i "workflow not found"

# 查看插件守护进程日志
docker logs docker-plugin_daemon-1 --tail 50
```

### 🔥 坑 7：公网访问配置问题

**场景描述**  
Dify 部署完成后，局域网访问正常，但公网用户访问时出现各种 404 和 URL 错误。

**问题现象**
- 公网访问后，API 请求返回 localhost 地址
- 页面跳转使用内网 IP，公网用户无法访问
- 部分静态资源加载失败

**根因分析**
1. Dify 内部使用 `localhost` 构建回调 URL
2. 前端代码使用 `CONSOLE_API_URL` 环境变量
3. FRP 端口映射配置不当

**解决方案**

**Step 1: 配置公网 URL 环境变量**
```env
# /opt/dify/docker/.env

# 关键配置：所有对外暴露的 URL
CONSOLE_API_URL=http://YOUR_PUBLIC_HOST:8082
CONSOLE_WEB_URL=http://YOUR_PUBLIC_HOST:8082
APP_API_URL=http://YOUR_PUBLIC_HOST:8082
APP_WEB_URL=http://YOUR_PUBLIC_HOST:8082
SERVICE_API_URL=http://YOUR_PUBLIC_HOST:8082

# CSRF 配置（允许所有来源）
CSRF_TRUSTED_ORIGINS=http://localhost:8082,http://YOUR_PUBLIC_HOST:8082
```

**Step 2: 配置 FRP 内网穿透**
```toml
# frpc-vm.toml (Windows 主机上运行)

serverAddr = "YOUR_PUBLIC_HOST"
serverPort = 7000
auth.token = "CHANGE_ME"

# 将 Linux VM 的 80 端口映射到公网 8082
[[proxies]]
name = "dify-vm"
type = "tcp"
localIP = "192.168.1.100"  # Linux VM 内网 IP
localPort = 80             # Linux VM 上的 Nginx 端口
remotePort = 8082          # 公网暴露的端口
```

**Step 3: 重启服务**
```bash
# 必须重启所有服务才能生效
cd /opt/dify/docker
docker compose down
docker compose up -d

# 验证公网访问
curl http://YOUR_PUBLIC_HOST:8082/health
# 应该返回: {"status":"ok"}
```

#### Q6: Nginx 反向代理的作用是什么？你是如何配置的？

**参考回答**
> **Nginx 的作用**:
> 1. **统一入口**: 所有请求通过 80 端口进入
> 2. **路由分发**: 根据 URL 路径将请求转发到不同的后端服务
> 3. **负载均衡**: 将请求分发到多个后端实例
> 4. **SSL 终止**: 处理 HTTPS 加密/解密
> 5. **安全防护**: 隐藏后端服务细节
>
> **路由配置要点**:
> ```nginx
> # API 请求 → API 服务
> location /console/api/ {
>     proxy_pass http://api:5001;
>     proxy_buffering off;  # SSE 流式响应需要
> }
> 
> # 插件请求 → 插件守护进程
> location /plugin/ {
>     proxy_pass http://plugin_daemon:5002;
> }
> 
> # 前端页面 → Web 服务
> location /console {
>     proxy_pass http://web:3000;
> }
> ```
>
> **关键配置**:
> - `proxy_buffering off`: SSE 流式响应必须关闭缓冲
> - `proxy_read_timeout 300s`: LLM 请求可能很慢
> - `proxy_set_header`: 传递原始请求信息

> -- 应用表：存储应用基本信息
> CREATE TABLE apps (
>     id UUID PRIMARY KEY,
>     name VARCHAR(255),
>     mode VARCHAR(50),           -- chatflow, agent, chatbot
>     app_model_config_id UUID,   -- 关联模型配置
>     workflow_id UUID,           -- 关联工作流
>     enable_api BOOLEAN
> );
>
> -- 模型配置表：存储应用使用的模型
> CREATE TABLE app_model_configs (
>     id UUID PRIMARY KEY,
>     app_id UUID REFERENCES apps(id),
>     provider VARCHAR(100),      -- 模型提供商
>     model_id UUID,              -- 关联凭据
>     model JSON,                 -- 模型配置
>     configs JSON                -- 其他配置
> );
>
> -- 工作流表：存储工作流定义
> CREATE TABLE workflows (
>     id UUID PRIMARY KEY,
>     app_id UUID REFERENCES apps(id),
>     version INTEGER,
>     status VARCHAR(20),         -- draft, published
>     graph JSON                  -- 工作流图结构
> );
>
> -- 提供商凭据表：存储加密后的 API Key
> CREATE TABLE provider_credentials (
>     id UUID PRIMARY KEY,
>     provider_name VARCHAR(100),
>     encrypted_config TEXT,       -- RSA 加密的配置
>     is_valid BOOLEAN
> );
> ```

#### Q12: 这个项目的技术选型有哪些考虑？

**参考回答**
> **Dify vs 自研**:
> | 对比项 | Dify | 自研 |
> |--------|------|------|
> | 开发速度 | 快，1-2 周 | 慢，2-3 月 |
> | 灵活性 | 中等 | 高 |
> | 维护成本 | 低 | 高 |
> | 可视化 | 有工作流编辑器 | 需自己实现 |
>
> **选择 Dify 的原因**:
> 1. 开源社区活跃，文档完善
> 2. 内置工作流编辑器，降低开发门槛
> 3. 支持主流 LLM 提供商
> 4. 有完善的 API 和插件机制
>
> **选择 Docker Compose 的原因**:
> 1. 简化多服务部署
> 2. 环境一致性保证
> 3. 易于扩展和迁移
>
> **选择 PostgreSQL 的原因**:
> 1. 支持 JSON 类型，适合存储配置
> 2. 性能稳定，社区活跃
> 3. Dify 官方推荐
