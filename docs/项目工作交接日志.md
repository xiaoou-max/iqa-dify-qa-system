## 一、项目一句话介绍

本项目是一套**自研的智能问答系统**，底层基于开源 **Dify**（docker 部署）构建了 5 个核心问答应用，并通过**自定义插件**（plugin daemon）接入**阿里云百炼**大模型、**Weaviate** 向量数据库做知识库检索，再通过 **ClickHouse** 查询洛阳房产销售数据，最后用 **FRP 内网穿透**把整个系统暴露到公网访问。

```
用户提问
   │
   ▼
Dify 应用（5个核心应用）
   │
   ├── 知识库检索 → Weaviate（广西交投文档 860 向量 + SQL示例 1 向量）
   ├── 大模型问答 → 阿里云百炼 qwen3.7-plus（走自定义插件）
   └── 数据库查询 → ClickHouse ly_fwxsxx 表（2021-2025 年，每年 27 条，共 135 条）
```

## 五、遇到的问题与解决方案（老师教学版）

> 按"现象 → 原因 → 解决 → 避坑"讲解，遇到同类问题可照此排查。

### 问题1：知识库检索命中 0 条，但系统看起来正常

**现象**：洛阳市房产销售智能问答工作流里，"知识检索-示例SQL"节点永远返回 0 条。

**原因（重点）**：Dify 知识检索节点的 `dataset_ids` 字段是**空数组**，等于没绑定任何知识库。节点配置了查询变量（`query_variable_selector`），但没绑定数据集，自然不会检索。另外它的 rerank 模型写的是 `gte-rerank`，而数据集实际用的是 `qwen3-rerank`，模型名对不上也会失败。

**解决**：通过 Dify 控制台 API 更新工作流草稿：
```
POST /console/api/apps/{app_id}/workflows/draft
```
把知识检索节点的 `dataset_ids` 改为 `["b3286485-f1d5-44b7-b9c3-2885a189202d"]`（SQL示例库），rerank 模型改为 `qwen3-rerank`。

**避坑**：排查"知识库没命中"时，第一件事就是检查工作流里知识检索节点的 `dataset_ids` 是否为空、`retrieval_mode` 是否正确、rerank 模型名是否与数据集配置一致。不要想当然认为"配置过就绑定了"。

---

### 问题2：Agent 应用只回"您好！我是XX助手…"客套话，不回答正题

**现象**：Agent 调用完工具（拿到了数据）之后，模型却输出自我介绍，完全忽略工具结果。

**原因**：自定义插件 `plugin_daemon_v3.py` 在把工具结果拼回消息时，如果末尾不是 user 消息，会追加一句 `user: "Hello"`。模型看到新的 user 消息 "Hello"，以为开启了新对话，就回客套话，工具结果被当成历史消息忽略了。

**解决**：把追加内容从 `"Hello"` 改为 `"请基于工具返回的结果，回答用户的原始问题。"`（plugin_daemon_v3.py 第 485-489 行附近）。

**避坑**：给大模型拼消息时，结尾必须是明确的"指令性"用户消息。工具结果后面直接跟 `user: "Hello"` 这类空泛文本，模型会理解成闲聊。这是 LLM 应用最常见的隐性 bug 之一。

---

### 问题3：Agent 应用不流式输出，一次性吐出整段回答

**现象**：回答等好久，然后"啪"一下全部出现，只有 1 个 chunk。

**原因**：插件声明的模型 `features` 里缺少 `"stream-tool-call"`。Dify 的 agent runner 看到模型不支持流式工具调用，就退回**阻塞模式**调用 LLM。

**解决**：在 `plugin_daemon_v3.py` 的模型声明里，给 qwen3.7-plus（和 qwen3.8-max）的 `features` 加上 `"stream-tool-call"`。改完后**必须清 Redis 缓存**（Dify 会缓存模型 schema）：
```
docker exec dify-redis redis-cli -a dify_redis_pwd_2026_Lp2c --no-auth-warning del *qwen3.7-plus*
```

**避坑**：改插件模型元数据后，光重启容器不够，**还要清 Redis 里的模型 schema 缓存**，否则改动不生效。这是 Dify 自定义插件的经典坑。

---

### 问题4：LLM 生成的 SQL 执行报错（ClickHouse 语法错误）

**现象**：ClickHouse 返回 `Syntax error: failed at position 18 ('\\')`，SQL 里的中文别名全被转义成 `\"区县名称\"`。

**原因**：大模型生成的 SQL 里中文别名带了转义引号 `\"`，直接执行当然报错。

**解决**：在查询服务 `services/query_database_ly/app/main.py`（第 88-91 行）执行 SQL 前做归一化：`sql = sql.replace('\\"', '"')`。

**避坑**：LLM 生成的代码/查询语句往往带多余转义，执行前做一次"引号归一化"是廉价又有效的手段。别指望模型每次都不出错。

---

### 问题5：Agent 调用工具报"数值范围校验失败（Output variable out of range）"

**现象**：Code/工具节点输出数值超范围被拒。

**原因**：Dify 配置里 `CODE_MAX_NUMBER=5`，把 code 节点可输出的数值上限限死成 5。

**解决**：在 `dify-deploy/docker/.env` 和 `docker-compose.yaml` 里把 `CODE_MAX_NUMBER` 改成默认最大值 `9223372036854775807`。

**避坑**：Dify 的环境变量有一些隐藏的限制性配置（`CODE_*`、`*_MAX_*`），出错时多搜 `.env` 里的限制项。

---

### 问题6：Weaviate 向量查询返回空结果

**现象**：混合检索（hybrid_search）查不到东西。

**原因**：诊断脚本把 `query_type` 传成了字符串 `"text"`，而 Weaviate API 需要枚举类型 `QueryType.TEXT_QUERY`。

**解决**：改用 `query_type=QueryType.TEXT_QUERY`。

**避坑**：Weaviate 的 Python 客户端对参数类型很严格，字符串和枚举不一样就静默返回空。查"为什么检索没结果"时，先确认客户端版本和参数类型对不对。

---

### 问题7：工作流里 LLM 输出 JSON 解析失败

**现象**：工作流下游节点报 JSON 解析错误。

**原因**：插件在流式传输时**重复发送了 content**（一段文本发了两次），导致 LLM 节点输出拼接出非法 JSON。

**解决**：在 `plugin_daemon_v3.py` 里修正流式分片逻辑，避免同一段 content 重复 append。

**避坑**：调试流式代理插件时，先在本地 dump 原始流（每次 `data:` 行的内容），确认每个事件只发一次。`diag_pd_raw.py` 就是干这个的。

---

### 问题8：Agent 调用工具报 `invalid_param`

**现象**：百炼 API 返回参数错误。

**原因**：插件把百炼流式返回的 tool_call **分片**直接透传，Dify 需要的是**完整**的 ToolCall 对象。

**解决**：在插件里把百炼返回的多个分片 tool_call 片段**累积拼接**成完整对象，再发给 Dify。

**避坑**：流式工具调用（stream-tool-call）的切片要自己拼装，这是流式 agent 的必修课。

---

### 问题9：数据库问答Excel 应用返回"随时告诉我！"（客套话）

**现象**：`3a5ee5f4` 应用调完工具后输出无关客套话。

**原因**：同问题2，工具结果后的用户消息拼接不当，模型把后续当成新对话。

**解决**：已在 `plugin_daemon_v3.py` 修复（追加"请基于工具返回的结果，回答用户的原始问题。"）。现已验证：流式输出 100 个 chunk，正确返回带 markdown 表格的完整答案。

**避坑**：同一个根因会表现为"多个应用同时坏"——遇到多个 agent 应用都不对劲时，优先怀疑公共的插件层，而不是逐个排查应用配置。

---

### 问题10：FRP 内网穿透失效，公网访问返回 nginx 404

**现象**：http://YOUR_PUBLIC_HOST:8081 打不开，返回服务器 nginx 的 404 页面。

**原因**：本地 **frpc 客户端没在运行**。frpc 没启动时，服务器 8081 端口的 HTTP vhost 代理没有可转发的客户端，流量落到服务器自己的 nginx 上返回 404。

**解决**：
1. 本地启动 frpc：`frpc -c frpc.toml`（或运行 start-services.bat 第 35 行）
2. 服务器端 frps 已配好 systemd 开机自启（`/etc/systemd/system/frps.service`），服务器重启不用管
3. 本地 frpc 目前**未**开机自启，电脑重启后需手动启动

**避坑**：判断"公网穿透有没有坏"，先看本地 frpc 进程在不在（`Get-Process frpc`），再看公网端口 TCP 通不通，最后看 HTTP 返回什么。404 = frpc 没连上；超时 = 端口没转发。

## 八、注意事项 / 已知坑

1. **ClickHouse 只有 2021-2025 数据**（每年 27 条）。查 2020 年或更早会返回空，不是 bug。
2. **LLM 生成的 SQL 引号要归一化**（问题4），这是必做项。
3. **改插件模型元数据要清 Redis 缓存**（问题3），否则不生效。
4. **frpc 电脑重启后要手动启动**，服务器 frps 已自启。
5. **agent 应用偶发空响应**：极少数情况请求 40 秒后无消息返回，重测即可恢复，不是持久故障。
6. 知识库检索节点绑定数据集时，确保 `dataset_ids` 非空 + rerank 模型名正确（问题1）。
